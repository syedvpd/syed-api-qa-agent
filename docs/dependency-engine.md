# Dependency Engine Architecture — Syed API QA Agent

## 1. Overview & Goal

In modern RESTful systems, endpoints are heavily interdependent. Executing `GET /users/{userId}` or `DELETE /orders/{orderId}` requires existing entity identifiers generated by preceding calls (e.g., `POST /users`). 

The **Dependency Engine** constructs a directed acyclic graph (DAG) of operations by analyzing OpenAPI schemas, path templates, and semantic relationships **without relying on any LLM**.

---

## 2. Dependency Inference Strategy

The engine utilizes three primary signals to discover parent-child links:

### 2.1 Explicit Path & Schema Matching (`HIGH` Confidence)
- When a path parameter `{userId}` directly matches a response schema property `userId` or `id` from an operation tagged with `user` or path `/users`.
- Example: `POST /users` returns `{"id": "usr_123"}` -> maps directly to path `/users/{id}` for `GET`, `PUT`, `DELETE`.

### 2.2 Heuristic Semantic Naming (`MEDIUM` Confidence)
- Entity-prefixed identifiers: A parameter named `productId` in `POST /orders` is matched against the response property `id` of `POST /products`.
- Singular/Plural normalizations (e.g., `categories` -> `categoryId`, `people` -> `personId`).

### 2.3 Type & Context Compatibility (`LOW` Confidence)
- Generic matching based on schema type and format (e.g., matching a UUID parameter with an available UUID response field).
- **Rule**: Destructive operations (`DELETE`, major `PUT` mutations) are **never** scheduled based solely on `LOW` confidence inference.

---

## 3. Graph Construction & Cycle Detection

1. **Node Representation**: Each OpenAPI operation is represented as a graph node $N_{method, path}$.
2. **Directed Edges**: An edge $A \to B$ indicates that operation $B$ consumes output parameters produced by operation $A$.
3. **Cycle Detection**:
   - Tarjan's or Kahn's topological sorting algorithm detects cyclical dependencies (e.g., $A \to B \to A$).
   - If a cycle is detected, the engine breaks the cycle by falling back to synthetic mock data generation for the non-essential parameter, ensuring execution never hangs or deadlocks.

```
       [POST /tenants]
              │
              ▼ tenant.id (HIGH)
       [POST /users]
              │
       ┌──────┴──────────────────────┐
       ▼ user.id                     ▼ user.id
[GET /users/{id}]            [POST /orders]
       │                             │
       ▼                             ▼ order.id
[PUT /users/{id}]            [GET /orders/{id}]
       │                             │
       ▼                             ▼
[DELETE /users/{id}]         [DELETE /orders/{id}]
```

---

## 4. Execution Plan Formulation (CRUD Chains)

When endpoints for an entity support standard lifecycle operations, the planner builds a coordinated CRUD suite:
1. **CREATE**: `POST /entity` (Captures generated identifier `{{entity.id}}`).
2. **READ**: `GET /entity/{{entity.id}}` (Verifies state matches created entity).
3. **UPDATE**: `PUT /entity/{{entity.id}}` or `PATCH /entity/{{entity.id}}` (Applies deterministic delta).
4. **VERIFY UPDATE**: `GET /entity/{{entity.id}}` (Asserts changes applied).
5. **DELETE**: `DELETE /entity/{{entity.id}}` (Executes deletion).
6. **VERIFY DELETED**: `GET /entity/{{entity.id}}` (Asserts `404 Not Found` or `410 Gone`).

Note: If an endpoint does not specify an operation (e.g., no DELETE is defined in the contract), the engine skips that step and never hallucinates routes.
